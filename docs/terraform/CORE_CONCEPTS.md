# Terraform — core concepts: working directory files

Based on `terraform/hashicorp-tutorials/docker-get-started`.

```
docker-get-started/
├── main.tf                  # written by you
├── variables.tf             # written by you
├── outputs.tf               # written by you
├── .terraform.lock.hcl      # generated by terraform init
├── .terraform/              # generated by terraform init
│   └── providers/registry.terraform.io/kreuzwerker/docker/4.2.0/windows_amd64/
│       └── terraform-provider-docker_v4.2.0.exe
├── terraform.tfstate        # generated by terraform apply
└── terraform.tfstate.backup # generated by terraform apply
```

## Configuration files (written by you)

Terraform reads **all** `.tf` files in the folder as one configuration. File names are only a convention.

- **`main.tf`** — the main logic:
  - `terraform { required_providers { ... } }` block — which providers are needed and which versions (`~> 4.2.0` = 4.2.x);
  - `provider "docker"` block — provider settings (here: connecting to Docker via a named pipe on Windows);
  - `resource` blocks — what to create (`docker_image`, `docker_container`).
- **`variables.tf`** — input variables (`variable "container_name"`) with type, description and `default`. Referenced as `var.container_name`.
- **`outputs.tf`** — values Terraform prints after `apply` (`container_id`, `image_id`). View them with `terraform output`.

## Generated by `terraform init`

### `.terraform/` — local cache

- Holds the **downloaded provider binaries** (and modules, if used).
- A provider is a separate program (`terraform-provider-docker_v4.2.0.exe`) that talks to a specific platform's API (Docker, AWS, etc.). Terraform itself cannot create anything without providers.
- The path mirrors the registry address: `registry.terraform.io / kreuzwerker / docker / 4.2.0 / windows_amd64` = registry / namespace / provider / version / OS_arch.
- **Not committed to git** (listed in `.gitignore`). Safe to delete — `terraform init` downloads it again.

### `.terraform.lock.hcl` — dependency lock file

- Pins the **exact provider version** (`4.2.0`) that `init` selected within the constraint (`~> 4.2.0`), plus the binary's **hashes**.
- Guarantees the same version on another machine / in CI, and that the binary was not tampered with.
- Equivalent of `package-lock.json` / `poetry.lock`.
- **Committed to git.** Do not edit by hand. To upgrade: `terraform init -upgrade`.

## Generated by `terraform apply`

### `terraform.tfstate` — state

- A JSON file that **maps your code to real resources** (container ID, image ID, all attributes).
- Terraform uses it to know what already exists and to compute the diff for `plan`.
- `serial` — counter of state changes; `lineage` — unique ID of this state.
- After `destroy` it stays with an empty `"resources": []` (as in this example now).
- **Not committed to git**: it can contain secrets (passwords, keys) in plain text. In team work it lives in a remote backend (S3, Terraform Cloud, etc.).
- Do not edit by hand — only via `terraform state ...`.

### `terraform.tfstate.backup`

- A copy of the **previous** state, made by Terraform before each write of a new `terraform.tfstate`.
- For manual recovery if something goes wrong. Also not committed.

## Summary

| File / folder | Created by | Purpose | In git? |
|---|---|---|---|
| `*.tf` | you | describes infrastructure | yes |
| `.terraform/` | `init` | cache of providers and modules | no |
| `.terraform.lock.hcl` | `init` | pins provider versions and hashes | yes |
| `terraform.tfstate` | `apply` | current state of real resources | no |
| `terraform.tfstate.backup` | `apply` | previous state | no |
